# 历史版本：A2/A3 物流与加工排队仿真

在第六周的参考布局和 MILP 布局上，增加带时间戳的物流、加工和资源排队过程。两种布局使用相同的整数任务、外部源与目标、到达时刻、车辆初始位置及调度规则，分别运行后进行同步回放。

## 打开展示

用浏览器打开 [A2_A3仿真展示.html](A2_A3局部回放.html)。页面内嵌仿真结果，无需安装 Python、启动服务或连接网络。

第六周的 [MILP交互展示.html](../../week6/汇报成稿/MILP交互展示.html) 也提供本周动态仿真的导航入口。保持仓库的相对目录结构即可互相跳转。

页面支持：播放、暂停、倍速、时间轴定位、任务跟踪，以及参考/MILP 布局的同步对比。地图中的设备颜色继续表示设备组，设备状态和队列另行标注；全程统计和当前时刻状态分别展示。

默认打开全厂总览，包含 **1116 个设备/设施实例、43 个 Bay 及完整轨道**。其中 1068 台是生产设备，48 个为固定 AMHS 设施；只有 A2/A3 的 48 台生产设备参与当前动态模型，其他设备为静态背景。A2/A3 内另有 2 个 STOCKER，也只作背景，未新增库存或调度仿真。全厂视野、A2/A3 局部与所选任务路线可以切换；两边地图同步缩放、平移，视野调整不改变仿真时刻或结果。

Bay 外框由设备矩形和所属轨道端点联合包络推导，属于区域定位示意，不能作为物理车间边界。InterBay2 没有设备但有公共轨道，因此仍显示在全厂总览中；完整视野同时保留设备外框、轨道节点及负 Y 坐标。

已保存的载货规划路径固定复用上周的节点顺序，避免重新计算时换成另一条等长最短路。空驶接货路线另外计算，并与载货规划线分开显示。默认聚焦所选批次及正在为它服务的车辆；开启其他车辆显示后，这些车执行的是各自任务，未必经过所选批次的规划线。物料等待和加工时锚定设备轨道端口，设备面板显示对应机器状态，不再把物料标记跳移到设备中心。

## 仿真范围与输入

- 两 Bay 的 48 个现有槽位；运输路径保留外部源、目标及必要的公共走廊。
- 从上周 59 道区域工序中选取 56 道单源、单目标工序。排除 `part_2:448`、`part_5:212`、`part_8:316`，因为它们的连续参考流存在多边界拆分，不能在保持逐任务端点一致的同时直接恢复原分流方案。
- 根据各选定工序的区域需求四舍五入，构建 560 次整数区域访问；这是一套生成的实验任务，**不是实际历史轨迹，也不是 560 个不同产品的完整生产路线**。
- 设备槽位按各布局保存的加工分配离散化。两种布局的同一任务具有相同的工序、加工需求、释放时刻、外部源和目标，仅槽位配置与对应任务位置发生变化。
- 本例没有正的区域内部连续工序转移，事件链为“外部来料—区域工序加工—外部出料”。

## 运行规则

一次区域访问包括：释放任务、请求车辆、等待与空车接货、装载、载货运输、卸载、设备排队、加工、出站请求和运送至外部目标。

首版采用有限局部车队、单车单 lot、先到先服务的搬运请求与设备队列。请求获得空闲车后还要等待其空驶到达源端；设备加工期间车辆释放，可服务其他请求。设备按实际槽位单台占用。

物理与时间参数是明确的情景假设：

- 假设原始坐标单位为毫米，以车辆类型表中的 `1500 mm/s` 作为恒速；计算统一转换为分钟。原坐标单位及 `Rail.MAX_SPEED=1` 的物理语义未完全确认，因此这些时间是**假设下的仿真分钟**，不能声称为现场实测秒数。
- 加工占用以原等效每 lot 加工时间除以 `0.85`，确定性折算有效机时，不显式模拟随机故障和停机。
- 装卸时间、局部车辆数与任务释放方式见页面及 `simulation/results.json` 中的参数说明；局部车队是实验资源配置，不是直接将原数据的 500 台车截取到这两个 Bay。
- 当前实验使用 4 辆车，每次装载和卸载各占用 0.5 分钟。设备进出缓存假设无限；加工完成即释放机器，等待出站车不阻塞下一批加工，装卸不额外锁定设备或端口。
- 先不模拟车辆追踪安全间距、轨道区段互斥、交叉口控制、死锁、故障、维护、抽检与返工。地图上的车辆可能共用轨道区段；资源等待表示等车或等设备，不能解释为已模拟真实交通拥堵。

## 场景与指标

提供常规的 7 天任务释放场景，以及明确标注的集中到达压力场景。压力场景用于观察有限资源下的排队，不是原始订单的实际历史到达过程。

每个场景都持续运行至全部任务完成，并额外统计 7 天窗口内的完成与未完成数。比较指标包括：

- 满载距离与空驶距离。
- 纯载货运输时间、等车时间、等设备时间。
- 搬运请求完成时间及 P95，区域任务停留时间。
- 设备/车辆利用情况、完成任务数与窗口内未完成任务数。

页面中的“全程结果”在场景切换时改变，不随播放器快慢改变；地图、队列和任务状态跟随回放时钟。倍速控制只影响观看速度。

上周 `0.582%` 是 59 道工序连续聚合流的局部加权距离改善。本周选取 56 道工序并离散化为有限任务，增加空驶、装卸和排队，其距离或时间改善应按本周仿真重新计算，**不要求也不应强行等于 0.582%**。

## 本次常规场景的结果

以下为同一套 560 次区域访问跑到全部完成后的统计，时间均是上述换算假设下的仿真分钟：

| 指标 | 参考布局 | MILP 布局 |
| --- | ---: | ---: |
| 平均单程搬运请求周转时间 / min | 6.146 | 6.015 |
| 每次区域访问的平均等设备时间 / min | 47.705 | 65.404 |
| 每次区域访问的平均区域停留时间 / min | 193.103 | 210.538 |
| 第 7 天已完成访问数 | 549 | 547 |
| 第 7 天未完成的已释放访问数 | 11 | 13 |
| 跑至全部完成的访问数 | 560 | 560 |

本次载货总距离下降约 **0.619%**，但设备排队增加，区域停留时间也增加。按设备组拆解，新增等待主要集中在 DE_BE_50；保存的加工分配在新布局中集中到更少的活跃槽位。这与静态运输目标未惩罚排队的特点一致，不能仅归因于某一台设备的移动，也不能把“优化布局”理解为所有动态指标都更好。

完整两场景指标见 [metrics.csv](../simulation/metrics.csv)，队列描述性分解见 [summary.json](../simulation/summary.json)。

## 复现

从仓库根目录执行。仿真引擎使用 Python 3.10+ 标准库的事件优先队列，不依赖 SciPy 或商业仿真软件。

```powershell
python week7/simulation/engine.py
python week7/visualization/build_viewer.py
python -m unittest discover -s week7/tests -p "test_*.py" -v
```

独立检查包含两个可手算的排队例、共同任务清单、加工与车辆资源互斥、车辆路径连续、已保存规划节点序列一致性、请求 FCFS、指标复算及窗口内完成/未完成守恒。

可选检查播放器交互（开发检查依赖 Linkedom，HTML 本身不依赖它）：

```powershell
cd week7
npm install --ignore-scripts --no-audit --no-fund
npm run test:ui
```

这项检查执行页面 JavaScript 和 DOM 交互，验证播放/暂停、倍速、拖动、场景切换、任务跟踪及结果稳定性。它不是实际浏览器布局或渲染验收；记录位于 [ui-checks.json](../validation/ui-checks.json)。

引擎读取 `week6/交互展示/milp-data.json` 和原始布局表，生成 `week7/simulation/results.json`；构建器将事件数据、样式及播放器打包为离线 HTML。改动场景参数后需重新运行引擎及构建器，单独调整动画速度不会重新仿真。

先跟踪 `part_5` 第 169 步的一次访问：解释参考方案的 ECH0163 与新布局 ECH0155 的加工位置差异，再看入程、加工、出程各阶段。随后播放多任务场景，观察等车、设备排队与完成情况；最后对比两种布局的全程统计，讨论静态运输距离收益是否转化成动态运行收益。
